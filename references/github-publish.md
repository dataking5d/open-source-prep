# GitHub 发布核验（按需读取）

本参考适用于用户已明确要求发布的阶段。它不授予发布权限；用户已给出的目标和授权也不需要机械重问。

## 1. 目标与能力

从会话取得 owner/name、可见性与许可选择。只缺关键条件时才问；继续完成不依赖答案的准备工作。
先查看可用专用工具的建库/上传能力及实际登录身份。不同入口可能对应不同账号；某个连接权限不足，不代表本机其他已授权入口也不足。

需要 CLI 时，按实际环境核对，例如：

```powershell
gh api user --jq '{login: .login, id: .id}'
gh repo view "$owner/$name" --json nameWithOwner,visibility,defaultBranchRef,url
```

普通用户仓库需匹配所有者权限；组织或协作仓库需核对实际的创建/写入权限。不能简单要求操作者登录名必须等于组织名。
不要输出原始 Token，也不要为了发布替换全局认证配置。已有可用授权入口时直接沿用。

## 2. 同名仓库与历史

不存在时，在已确认目标下创建空仓库，不自动初始化会与候选冲突的 README/许可。
404 可能来自无权限，不能在身份未核实时直接断言不存在。

若仓库已存在，读取默认分支、内容、提交关系及权限：
- 用户已授权更新现有库时，列出差异后按授权正常提交或走 PR；尊重保护规则。
- 目标或覆盖范围仍不明确时，暂停对应远程写入并问清楚。
- 不把同名冲突自动转成强推、替换 origin、修改可见性或另建用户未选的后缀仓库。

公开既有私有仓库会暴露其可达历史，不只是当前 main。历史含私密内容时，先准备适当的隔离发布方案；不要只建立孤儿分支就宣布整个仓库已清理。

## 3. 本地发布副本

从审计清单或已经逐字节核验的 ZIP 提取到新的上传副本。ZIP 要先检查路径穿越、重复条目、链接与文件哈希。
不要全量复制含本地依赖的测试目录，也不要直接推原私有仓库。

新干净首发可在该副本初始化新 Git 历史；应保留历史的更新场景则按相应基线操作。
提交身份采用当前目标适用的身份；需要 noreply 邮箱时从实际账号信息或已有核实配置取得，不套用旧用户 ID。不修改全局 Git 身份。

暂存后读取真实索引清单和 blob，核对与候选一一对应。留意全局忽略、换行转换和 attributes/filter；不能仅凭 `git status` 看起来干净就认为字节一致。
网络配置沿用当前有效设置。实际失败后才诊断代理和权限，调整限本次命令或该副本；不强制固定端口，不因一次失败轮流换账号、协议和后端。

## 4. 上传和失败后的状态

按已确认的可见性建库，推送候选提交，保存仓库 URL、本地/远程提交、文件数和核验状态。
独立项目可分步上传；每个成功步骤立即保存回执，避免中断后重复创建或误覆盖。

某步失败时先读取回执与实际远程状态，只补未完成步骤。鉴权、风控、冲突或未知结果不要循环重试；完成不受影响的本地工作后明确指出所缺条件。
不把一次非零退出后的猜测记为成功，也不为回滚擅自删除已经创建的仓库。

## 5. 远程复核

通过实际远端 API 或可靠读取方式检查，而非仅看可能未更新的本地 `origin/main`：

```powershell
gh api "repos/$owner/$name"
gh api "repos/$owner/$name/commits/$branch"
gh api "repos/$owner/$name/git/trees/${branch}?recursive=1"
gh api "repos/$owner/$name/license"
```

核对所有者、可见性、默认分支、远程 commit，以及文件路径/类型/blob 哈希。递归树被截断时应分页/分树补齐，不能把部分列表当完整通过。
需要时独立读取原始文件或按 Git blob 算法核对。发布包 SHA-256 与 Git blob ID 是不同口径，不能直接相等比较。
确认不存在未经批准的其他远端分支、标签或历史材料；新干净首发核对提交数符合预期。

许可证元数据可能晚于文件出现。先核对实际 LICENSE 字节，再做一次合理的后续识别检查；记录未识别状态，避免无界轮询或反复提交相同文件。

完成后交付准确链接、可见性、实际核验结果与公开副本位置。源码改变后需重新验证受影响项、生成新包，不能沿用旧哈希发布。
